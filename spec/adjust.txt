We have confirmed the backend is working.

Direct backend test:

```text
POST http://127.0.0.1:8000/api/auth/register/
```

returns:

```text
HTTP/1.1 201 Created
```

and returns the created user successfully.

The browser error is now confirmed as:

```text
Access to fetch at 'http://127.0.0.1:8000/api/auth/register/'
from origin 'http://localhost:3000' has been blocked by CORS policy:

The value of the 'Access-Control-Allow-Credentials' header
in the response is '' which must be 'true'
when the request's credentials mode is 'include'.
```

The same happens for:

```text
/api/accounts/me/
```

## Root cause

The frontend API client currently forces:

```ts
config.credentials = 'include';
```

for every request.

The backend is using DRF Token authentication and does not currently return:

```http
Access-Control-Allow-Credentials: true
```

Therefore the browser rejects the cross-origin request.

## Required fix

Work in:

```text
src/lib/api/client.ts
```

Remove the unconditional:

```ts
config.credentials = 'include';
```

Do NOT replace it with a backend CORS wildcard.

The frontend authentication architecture is token-based and already sends:

```http
Authorization: Token <token>
```

when a token exists.

Keep this behavior unchanged.

## Important

Do not remove:

```ts
Authorization: `Token ${token}`
```

Do not change the API base URL behavior:

```ts
const API_BASE_URL = process.env.NEXT_PUBLIC_API_URL || '';
```

Do not change registration, login, logout, or `/api/accounts/me/` endpoints.

Do not disable authentication.

Do not set:

```python
CORS_ALLOW_ALL_ORIGINS = True
```

Do not add unnecessary credentialed CORS support just to accommodate the previous frontend behavior.

## Cookie/CSRF handling

Inspect the current API client carefully.

The code currently also attempts to add:

```http
X-CSRFToken
```

from the `csrftoken` cookie for mutating requests.

Determine whether that is actually required for the application's token-authenticated API.

Because the application is using DRF Token authentication, do not introduce a new cookie/session authentication architecture.

Only retain cookie credentials/CSRF behavior if the existing backend contract proves a specific endpoint requires it.

Do not make speculative authentication changes.
